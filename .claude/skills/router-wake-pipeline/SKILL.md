# The Wake Pipeline

The rules are CLAUDE.md → Architecture's; this skill is the reasoning and the mechanism behind them. Where the two disagree, the charter wins and this skill is corrected.

## One Harness Instance per Agent — the Per-Agent Serializing Multiplexer

The constitution makes an agent's identity **unified across every input path** (`constitution.md` → "Sovereignty and Governance": *"Each agent acts under its own identity — and that identity is singular"*). Every channel that can address an agent — a GitHub event, a BaseCradle Event Delivery, any future source — converges on **one identity-and-memory locus**: **one harness instance per agent**, running as that agent's own OS user, against its own home and memory. The harness *type* (Claude Code / basecradle-harness / cradle) is shared across agents; the per-agent *instance* is not. The router has **many inputs and one terminus per agent**, so it is a **per-agent serializing multiplexer** — `N inputs → one harness instance per agent`:

- **An input routes to the agent's existing harness instance — never stands up a second.** The `github` route's handoff issues and the `basecradle` route's Event Delivery reach the **same** instance for an agent (same OS user, same home, same memory). Adding an input is wiring a new source onto an existing terminus, never forking the agent.
- **Inputs serialize into one ordered stream per agent.** A harness instance is a single-session-at-a-time runtime over one memory/transcript store; two live sessions writing it concurrently is corruption / split-brain — the exact failure the unified-identity rule exists to prevent. The router never fans two inputs into two parallel wakes for one agent. Two mechanisms enforce it, both keyed by the agent's `harness_key` (its OS-user slug — the instance's identity):
  - **The wake scheduler** (`scheduler.WakeScheduler`, #182) holds a FIFO queue per agent and never submits a second wake for an agent while one is running, so no worker thread is ever parked waiting on an agent. Its pool (`BASECRADLE_ROUTER_WAKE_LANES`) caps how many *distinct* agents are mid-wake at once — a busy agent holds exactly one lane — so it is a capacity ceiling, never a per-agent limit. An idle agent's wake (the probe's included) waits behind at most the `lanes` currently-running wakes, one per busy agent, never behind a busy agent's queued backlog — so a slow probe while every lane is busy is a reason to raise `BASECRADLE_ROUTER_WAKE_LANES`, not a dead edge.
  - **The per-agent lock** (`concurrency.AgentLocks`), held across the wake in `pipeline.Pipeline.execute`, is the last-line correctness net for the same invariant. Because the scheduler guarantees single-in-flight, the lock is always uncontended.

  Both are keyed on the **agent**, deliberately **not** the repo: a repo is a GitHub-shaped notion a non-GitHub input need not carry, whereas every input resolves to an agent.
- **An ordered stream is not a wake per delivery.** At dispatch, a delivery that a successful wake of the same agent on the same stream (issue or timeline) already read collapses into that wake (`coalesce.WakeCoverage`). A delivery whose work ended while it waited is dropped by its route's `recheck`. So N deliveries behind a running session cost at most one follow-up, and a closed issue wakes no one (#272; the platform route's timelines since #311). Coverage is keyed per agent because a timeline is shared by every agent viewing it, and what one agent's session read says nothing about another's. Both are route opt-ins; a route that opts into neither keeps one delivery, one wake.
- **Unified memory, not unified conversation.** A GitHub PR thread and a BaseCradle Timeline are *different conversations sharing one memory + identity*. The router preserves each event's source/thread context so the harness can map each input to its own session while all draw on the one shared memory; that mapping (per-source sessions, cross-session answerability) is the harness's half, owned by `basecradle-harness`.
- **Bijection.** One agent ↔ one harness instance. The router never points one agent's inputs at two instances, nor one instance at two agents. *Different capability per channel (heavy code work vs. light chat) is one harness with modes/tools — never two harnesses; different capability ≠ different brain.*

## A Stop Is a Stop, Never a Crash to Retry

A wake killed by a stop signal (`wake.STOP_SIGNALS`: exit `-15`/`-9`, i.e. `sudo` died by the signal — only a signal from outside the wake does that) raises `wake.WakeStopped`, which is deliberately **not** a `WakeError`, so the retry never sees it (#386). Killing a runaway wake is the operator's one tool against it; read as a crash, it re-woke the agent on the same delivery and, once the retries ran out, wrote the `stage=wake outcome=failed` line the NOC's *Wake Failed* alert pages on — paging the operator who used the tool. `Pipeline._wake` ends a stopped wake on the spot: one `event=wake_stopped` WARNING, `stage=wake outcome=stopped`, `wake_end outcome=stopped`; the delivery is marked done in the deduper, the session covers what it had read (its start is drawn like a success's), and **no** evidence is recorded — a stop is neither the edge failing nor a gate refusing, and never an `ok`. `143`/`137` stay crashes: a signal death *inside* the wake (the harness's watchdog, the OOM killer) surfaces as `runuser`'s 128+N, indistinguishable from a crash. The sanctioned stop is `deploy/bin/stop-wake`, run as root: it signals the wake's whole process *tree* plus every process of the agent's account carrying the wake's `BASECRADLE_DELIVERY_ID` (which survives reparenting), because the wake has no process group of its own — it shares the daemon's. The chain's relays never double a SIGTERM (#404): `sudo` and `runuser`'s child are left to them (a relay is a `sudo` or `runuser` found by its **position** on the path down from the wake's root `sudo` — position and name, never a name or uid alone: the wake's `sudo` has the router's real uid, and a session process can take either name), since a second TERM inside `runuser`'s 2 s pre-SIGKILL sleep cuts the binary's grace to milliseconds; `runuser` is signalled directly and parents before descendants, so it always catches and re-raises. `tests/test_stop_wake_tree.py` proves it on a real tree, as root in CI.

## A Temporary Failure Is Retried Later, as a Job Queue Retries (#527)

A wake that exits `wake.TEMPFAIL_EXIT` (75, `EX_TEMPFAIL`) gave up on an outage, and the quick retry's three tries in ten seconds meet the same refusal, so `wake.WakeTempFailed` (a `WakeError` subclass, so every older `except WakeError` still holds) leaves `with_retry` at once and `Pipeline._wake` hands the delivery to `retry.RetrySchedule`: tried again at about 1, 5 and 30 minutes, `stage=wake outcome=deferred` plus one `event=wake_retry … retry_at=` line, never marked done, no wake evidence. The fourth attempt's temporary failure is the delivery's failure (`outcome=failed attempts=4`). Every other exit keeps the quick retry. A probe is never scheduled: its exit 75 is an unarmed agent, still a failure.

The shape is `@origin`'s correction on #527 (2026-11-20), "the way DHH would": **each delivery has its own schedule, and nothing carries from one delivery to the next.** There is no reset, no per-stream state, no join. What makes that enough:

- **A success cancels the waiting retries it read** (`Pipeline._cancel_covered` → `RetrySchedule.cancel_covered`), by the coalesce rule — same agent, same stream, event before the session's start — written to the file so it holds across a restart, where `WakeCoverage` (memory only) would not. Each cancelled delivery gets `decision=coalesced into=<delivery>`.

- **A retry is a delivery dispatched again**, submitted to the agent's queue and run through every gate in `execute`. The coalesce gate is the net for a retry already queued when a covering success landed. A duplicate of a waiting delivery (one GUID, two Apps) is collapsed into its schedule (`stage=dedup reason=retry_pending`) rather than waking into the outage. Recheck drops it, the breaker refuses it, a stop ends it, exactly as for any delivery.
- **`settle` in `execute`'s `finally` ends every retry's schedule** unless the dispatch re-armed it (a temporary failure with attempts left, or the wake lock). It pops only an entry still marked *due*, so re-arming is what keeps one alive; a gate added later ends a retry's schedule by construction.
- **The wake lock is the one gate that waits**: a due retry under it is re-armed after its own step's wait, never dropped (so a long hold costs one line per step, never one a minute). A first wake under it is refused as it always was.
- **The attempt is looked up, not carried**: `RetrySchedule.attempt` answers a due retry's number for that `(agent, dedup_key)`, else 1. It reaches the wake as `wake-runner --attempt n/of` → `BASECRADLE_WAKE_ATTEMPT`/`_ATTEMPTS`, and rides the bookends' prefix. `attempt=` means the delivery's attempt on every line; the quick retry's tries inside one attempt are `try=N/3`.
- **The try is counted once, by the quick retry** (#533): `with_retry` hands its operation its own try number, and `Pipeline._wake` passes it on as `WakeTry(tried, attempts)`, the bound being the very `attempts` it gave `with_retry` (1 for a probe). It reaches the wake as `wake-runner --try n/of` → `BASECRADLE_WAKE_TRY`/`_TRIES`, on every wake, a probe at `1/1`, so the harness can write no final failure for a try the router repeats. Never a second counter beside the loop: the pair must be exact, since the harness reads `TRY < TRIES` as another try following. `quick_try` has no default on `Waker.wake`, so no wake launches without it. `stop-wake` parses that argv, so `test_the_parser_reads_exactly_the_argv_the_router_assembles` builds it with every attempt and try shape.
- **It persists** to `/var/lib/basecradle-router/wake-retries.json` through `statefile.atomic_write` (the evidence store's writer), and the server fires what was left only after `warm_routes`, so a restored retry's recheck reads warm state.

## The Wake-Rate Circuit Breaker — the Cross-Agent Runaway Backstop

Because the router is the **single chokepoint for every wake** — every source's deliveries funnel through one wake path, and it alone has the **cross-agent view** of how often each agent is woken — it is the natural home for the backstop that catches a runaway loop the per-agent harness layer can't: a harness that crashes before it can self-track, a multi-agent ping-pong, a novel loop from a drop-in `tools/` or MCP server. This is the **wake-rate circuit breaker** (`breaker.WakeRateBreaker`), consulted in `pipeline.Pipeline.execute` **inside the per-agent lock and immediately before the wake**.

- **It counts true dispatch rate, not delivery rate.** Sitting *inside* the lock (behind the scheduler, which already runs same-agent wakes one at a time) means it measures the rate at which wakes actually fire: a runaway fires back-to-back as each completes and trips; a legitimate burst of queued deliveries drains one slow wake at a time and never does. It tracks a rolling window per **agent** (keyed on `harness_key`, same as the lock) and per **(agent, stream)** — one looping timeline or handoff issue, via `Event.stream_key` — so a single sub-stream spinning trips even under the agent's overall cap. A wake is refused if **either** scope is over threshold.
- **A trip is loud and never silent.** Over the cap → stop dispatching that scope's wakes, record a visible `BREAKER`/`IGNORED` decision (the same "deliberate, never silent" posture as the route's `IGNORED`/`WOKE` lines), and escalate with an `event=breaker_tripped` `ERROR` the NOC can detect. Refusing a wake loses no data — the platform's cursor-paginated read API is the source of truth, push is best-effort — so a tripped agent only *pauses* its push.
- **It auto-resets.** Once the cooldown elapses and the window clears, wakes resume (logged); a transient burst self-heals, never latching forever. Thresholds are a **generous sanity cap**, tunable via `router.env` (`BASECRADLE_ROUTER_WAKE_BREAKER_MAX`/`_WINDOW`/`_COOLDOWN`/`_STREAM_MAX`; see `deploy/README.md`), defaulted so legitimate multi-peer activity never trips it.
- **Defense-in-depth, no coupling.** It is independent of the harness's own per-agent/per-timeline self-breaker (the sibling harness-side layer): no router↔harness protocol, each trips on its own view, they compose without coordination.
- **Its trip line is a NOC alarm's needle.** The `breaker_tripped` line is what the fleet's *Circuit Breaker Tripped* alarm extracts, and it exists only on the failure path; the `log-grammar:breaker_tripped` probe is how a rename gets caught (the `router-claims-and-probes` skill).
